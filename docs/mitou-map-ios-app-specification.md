## 1. プロダクト定義

### 1.1 目的
iPhoneが自動で位置ログを取り続け、「行ったことがある場所」を霧が晴れた領域として地図に可視化し、未訪問エリアへの外出を促す。ユーザーの行動範囲を広げ、日常に探索の動機を作る。

### 1.2 コアバリュー
- **ゼロ運用**: 一度許可すれば、アプリを開かなくても記録が続く
- **電池を犠牲にしない**: 常時記録でもバッテリー影響を体感させない
- **データは自分のもの**: 全データ端末内保存。サーバー送信なし。いつでもエクスポート可能

### 1.3 成功指標(個人利用MVP)
| 指標 | 目標 |
|---|---|
| 記録の連続稼働 | 7日間、手動操作ゼロで欠損なし |
| バッテリー影響 | 標準モードで1日あたり1%未満 |
| 行動変化 | 提案を受けて未踏セルを訪問した回数: 週1回以上 |

### 1.4 スコープ
| フェーズ | 内容 |
|---|---|
| MVP (v1.0) | 自動ログ / 霧マップ / 未踏提案 / 到達通知 / タイムライン・GPXインポート / エクスポート |
| v1.1 | Apple Watchアプリ+コンプリケーション / 週次レポート通知 / iCloud同期 |
| 将来 | 実績システム / 地域メッシュ統計連携(人口・POI密度) / 精密経路モード |

## 3. 位置ログ取得仕様(本アプリの心臓部)

### 3.0 前提: iOSに「1時間おき」の保証はない

設計の出発点として明記しておく。**iOSには時計通りにバックグラウンド処理を実行させる仕組みが存在しない。** cronもタイマー起動もOSが許していない。`BGAppRefreshTask` に1時間を指定することはできるが、実際の発火タイミングはOSが使用パターン・電池残量から決めるものであり、間隔は保証されない。

加えて、仮に1時間おきの取得が実現できたとしても、それは霧マップにとって粒度が粗すぎる。徒歩4km/hで1時間移動すると250mセルを約16個通過するが、1時間おきのサンプリングで拾えるのは1個だけである。**時刻駆動を主軸にすると踏破記録の大半を捨てることになる。**

したがって本アプリは **移動イベント駆動を主軸(L0〜L2)とし、時刻駆動(L3)は「同じ場所に留まり続けている」ことの裏取りに用途を限定する**多層構成をとる。

### 3.1 記録レイヤー構成

| 層 | 名称 | 使用API | 駆動 | アプリ終了後の再起動 | 電池 | 既定 |
|---|---|---|---|---|---|---|
| L0 | 常時ベース | `startMonitoringSignificantLocationChanges()` | 約500m移動・基地局変化 | ✓ | ほぼゼロ | ON |
| L1 | 滞在検出 | `startMonitoringVisits()` | 到着 / 出発 | ✓ | ほぼゼロ | ON |
| L2 | 追尾ジオフェンス | `CLCircularRegion` の自己更新(§3.2) | 半径150mからの離脱 | ✓ | ほぼゼロ | ON |
| L3 | 時刻ハートビート | `BGAppRefreshTask` + `requestLocation()` | 1時間目安(**OS裁量**) | ✗ | ほぼゼロ | ON |
| L4 | 精密モード | `startUpdatingLocation()` + background updates | 連続(数十m) | ✗ | 約5%/時 | OFF(手動) |

設計判断:

- **L2 が本構成の中核。** SLCの約500m粒度とセル粒度250mの差を埋める唯一の低電力手段であり、かつアプリが終了していてもOSが起こしてくれる。L0 だけではセル1個分を丸ごと飛ばす移動が日常的に発生する
- **L3 は主軸にできない。** 時刻駆動に見えるが実体はOS裁量であり、アプリを開かない日は発火頻度が落ちる。滞在中の裏取り専用と割り切る(§3.3)
- **L4 は「散歩の軌跡を残したい」欲求向けのオプション。** MVPの価値は L0〜L3 だけで成立する

### 3.2 L2 追尾ジオフェンスの仕様

記録を1点採用するたびに、その地点を中心とした半径150mの `CLCircularRegion`(`notifyOnExit = true`)を登録し直す。離脱イベントでアプリが起床 → 記録 → 新しい現在地でアンカーを再登録、というループを回す。

- identifier は固定文字列1つ(`trail.anchor`)を使い回す。毎回同じIDで置換することで、監視リージョンが際限なく溜まるのを防ぐ
- 半径150mはセル辺長250mに対して十分に細かく、かつGPS誤差による誤検知が頻発しない下限として選定
- **リージョン枠の予算**: iOSのリージョン監視上限はアプリあたり20件。本アプリの使用は L2 アンカー1件 + §6.4 のアクティブクエスト1件 = **常時2件**。残り18件は将来用に確保する

### 3.3 L3 時刻ハートビートの仕様

- タスク識別子を Info.plist の `BGTaskSchedulerPermittedIdentifiers` に登録する
- `BGAppRefreshTaskRequest.earliestBeginDate = .now + 3600`
- **実行の冒頭で必ず次回分を再スケジュールする。** リクエストは発火時に消費されるため、再登録を忘れると二度と発火しない
- 処理本体は `requestLocation()` による単発測位1回のみ。実行時間の割り当ては約30秒しかないため、`task.expirationHandler` で確実に打ち切る

制約(仕様として受け入れる):

- 実際の発火間隔はOSが使用パターン・電池残量・低電力モードから決める。1時間は下限の希望値でしかない
- ユーザーが強制終了(スワイプ)した後は、次に手動起動するまで発火しない
- アプリを一度も開かない日は発火頻度が落ちる

→ **L3 は保険であり、記録の主軸は L0〜L2 である。** L3 が丸一日発火しなくても、移動さえしていれば L0〜L2 が記録を埋める。

### 3.4 起動経路

- 権限: 「常に許可」+ 正確な位置。取得は §7.1 の段階的オンボーディングで行う
- Background Modes: `location` を有効化(L4 用)
- `UIApplicationDelegateAdaptor` を導入し、`application(_:didFinishLaunchingWithOptions:)` で `launchOptions[.location]` によるバックグラウンド起動を検知する
- **delegate の設定と L0〜L2 の再 arm は、UI表示を待たず起動時に無条件で実行する。** CoreLocation は delegate が存在して初めてイベントを配信するため、ここが遅れると起動理由となったイベント自体を取りこぼす
- LocationEngine / Store は SwiftUI の Scene ライフサイクルから切り離す。`@StateObject(wrappedValue:)` は autoclosure であり、Scene の body が評価されるまでインスタンス化されない。UIに依存した保持では、バックグラウンド起動時に記録が一切走らない
- バックグラウンド記録は `mainContext` とは別の `ModelContext` を使う
- 記録処理は起動から3秒以内に完了させる(§9)

### 3.5 統合記録パイプライン

全レイヤー・Watch・インポートの**唯一の入口を `LocationStore.ingest` に一本化する**。フィルタを複数箇所に分散させない。

```
L0 / L1 / L2 / L3 / L4 / Watch / Import → LocationPayload
 → [唯一の入口] LocationStore.ingest(payload, policy:)
 → 精度フィルタ  : horizontalAccuracy < 0 は棄却 / > min(100m, セル辺長/2) は棄却
 → 鮮度フィルタ  : |timestamp - now| > 300秒 は棄却(policy = .historical では適用しない)
 → 重複排除      : 直前採用点から 60秒未満 かつ 50m未満 は棄却
 → 同一ID排除    : 既存 LocationSample と id 一致なら棄却(インポート再実行対策)
 → Point保存 → 所属セル計算 → 未踏セルなら Cell新規作成(初到達日時記録)
 → 到達がアクティブなクエスト先セルなら達成処理(§6.4)
 → L2 アンカーを現在地へ再登録(§3.2 / policy = .live のみ)
```

- 閾値は `Sources/Shared` に `RecordingPolicy` として定数化し、ユニットテストの対象とする(§10.1)
- 精度閾値は **`min(100m, セル辺長/2)`**。250mセルでは100m。誤差がセル半径を超える測位を採用すると、通っていないセルが踏破済みになる
- `policy` は `.live`(L0〜L4 / Watch)と `.historical`(インポート)の2値。鮮度フィルタの適用有無と、L2 アンカー再登録の有無が異なる。過去データの取り込みで現在地のジオフェンスを動かしてはならない

#### 精度閾値100mと L0 の緊張関係(既知のトレードオフ)

L0(SLC)の配信は基地局ベースになる場面があり、`horizontalAccuracy` が数百mになることがある。100m閾値ではこれらが棄却され、**L0 の採用率が想定より下がる可能性がある**。

それでもこの設計では閾値を緩めない。誤差500mの1点でセルを踏破済みにすると、訂正UIを持たない本アプリでは唯一のデータ資産が不可逆に汚れるためである(欠損は取り返せるが、誤記録は取り返せない)。

L2 が150m粒度で移動を拾うため、L0 の棄却は多層構成の中で吸収される想定。**§10.3 のフィールドテストでレイヤー別の採用/棄却件数を計測し**、L0 の棄却率が高すぎる場合の対処は「閾値を緩める」ではなく「セル粒度を500mに上げる(閾値も連動して125m→250mに緩む)」を第一候補とする。

### 3.6 レイヤー間の重複について

L0 と L2 は同一の移動に対して同時に発火しうる。これは**意図的な冗長性**であり、削ってはならない。片方が取りこぼしても他方が拾うことが多層構成の目的そのものである。

二重記録は §3.5 の重複排除(60秒未満 かつ 50m未満)が吸収する。したがって層を重ねてもストレージとセル踏破判定に影響は出ない。

### 3.7 エッジケース
| ケース | 挙動 |
|---|---|
| 権限を「使用中のみ」に格下げされた | L0〜L3 が全停止。バナーで常時記録が止まっている旨を表示 |
| 「正確な位置」がOFF(`reducedAccuracy`) | 誤差が数kmとなり全点が精度フィルタで棄却される。**記録が無言で止まる最悪ケースのため、格下げとは別の専用バナーで再許可を促す** |
| 位置精度が悪い(地下・屋内) | フィルタで棄却。欠損は許容(セル単位なので影響小) |
| 強制終了(スワイプ) | L0/L1/L2 はOSが再起動して配信。L3 は次回手動起動まで停止 |
| 低電力モード | L3 は発火しない。L0〜L2 は継続 |
| 端末再起動 | L0/L1/L2 はOSが復元するが、依存せず起動直後に明示的に再 arm する |
| 機内モード/圏外 | GPSは動作するため記録継続 |
| 海外 | グリッドは全世界一様なのでそのまま動作 |

### 3.8 検証方法
- L0 / L1 / L2 はシミュレータで正確に再現できない。**実機をバックグラウンドに回した状態での実移動が必須**(§10.3)
- L3 は Xcode デバッガから `_simulateLaunchForTaskWithIdentifier` で強制発火させて動作確認できる。ただし発火間隔そのものの検証は実運用でしか行えない
- L4 は Xcode の位置シミュレーション用GPXで再現可能(§10.2)

## 4. セル(メッシュ)仕様

### 4.1 体系の比較
| 体系 | 長所 | 短所 |
|---|---|---|
| **独自等角グリッド(採用)** | プロトタイプとロジック・データ互換。全世界一様。実装最小 | 統計データとの直接照合不可 |
| JIS地域メッシュ (X 0410) | 国勢調査等の統計と直結(将来のPOI/人口スコアに有効) | 日本国内限定。コード変換実装が必要 |
| Geohash | 汎用・共有しやすい | 緯度でセル縦横比が変わり見た目が不均一 |

採用: 独自等角グリッド。将来の統計連携時に「独自グリッド→地域メッシュ変換関数」を追加すれば両立できるため、今はコストを払わない。

### 4.2 定義
- `cellKey = "\(floor(lat / s))_\(floor(lng / s))"`、s ∈ {0.0025, 0.005, 0.01}(約250m / 500m / 1km)
- 記録時に**3粒度すべてのセルを同時登録**する(粒度切替を再計算なしで即時反映するため。ストレージ増は軽微)

### 4.3 データモデル(SwiftData)
```swift
@Model final class Point {
  var lat: Double; var lng: Double
  var timestamp: Date
  var accuracy: Double
  var source: String   // "slc" | "visit" | "precise" | "import"
}
@Model final class Cell {
  @Attribute(.unique) var key: String   // "size:i_j" 例 "0.005:7212_27934"
  var sizeClass: Int    // 0=250m 1=500m 2=1km
  var firstVisit: Date
  var lastVisit: Date
  var visitCount: Int
}
@Model final class Quest {
  var targetKey: String
  var createdAt: Date
  var completedAt: Date?
  var distanceM: Double
}
```
インデックス: `Cell.key`(unique)、`Point.timestamp`。

## 5. 霧レンダリング仕様

- `MKOverlay` 準拠の `FogOverlay`(全世界矩形)+ カスタム `FogOverlayRenderer`
- 描画: `draw(_ mapRect:zoomScale:in:)` で (1) 対象mapRectを霧色 `#0E1520` α0.78 で塗り、(2) そのrectに交差する踏破セルを blend mode `.clear` でくり抜く
- 踏破セルはメモリ上の `Set<CellKey>` + 空間インデックス(i,j範囲クエリ)で照会。タイル単位描画のためセル数が数万でも一定コスト
- 晴れた縁のぼかし: くり抜き矩形に2ptのソフトエッジ(v1.0はオプション、負荷次第で削る)
- 粒度切替・霧ON/OFFは `setNeedsDisplay()` のみで反映

却下案: `MKPolygon` + interiorPolygons(プロトタイプ方式)。セル数千で頂点更新コストが増えるため、タイル描画方式を採用。

## 6. 未踏提案エンジン(QuestEngine)

### 6.1 MVPアルゴリズム
プロトタイプと同一の螺旋探索を基礎に、スコアリングを追加。

```
候補 = 現在地セルから螺旋探索した未踏セル上位N(=30)
score(c) = w_d · proximity(c)        // 近いほど高い(徒歩30分内を優遇)
         + w_p · poiBonus(c)         // MKLocalSearchでカフェ/公園/神社等がヒットすれば加点
         + w_n · directionNovelty(c) // 過去の提案・移動方位と異なる方角を加点
初期重み: w_d=1.0, w_p=0.6, w_n=0.4(設定画面で調整可、検証対象)
```

### 6.2 提案トリガー
| トリガー | 内容 |
|---|---|
| 手動 | マップ画面のボタン(MVP必須) |
| 週末プッシュ | 土日 9:00、その週に未踏訪問がなければ通知(設定でOFF可) |
| 週次レポート | 日曜 20:00「今週 +12セル踏破、踏破率 x%」(v1.1) |

### 6.3 提示内容
方角+距離(「北東へ 1.2 km」)、セル中心座標、POIヒット時はその名称、マップ上に破線とターゲット表示。「マップアプリで経路を開く」ボタン。

### 6.4 到達判定
クエスト受諾時にターゲットセル中心へ **半径=セル辺長/2 のジオフェンス**(Region Monitoring)を登録。入域でアプリが起こされ、達成記録+通知「🌫→☀ 霧が晴れました」。ジオフェンスは最大20件制限があり、うち1件は §3.2 の L2 追尾アンカーが常時占有するため、アクティブクエストは常に1件とする(合計2件使用)。

## 7. 画面仕様

| 画面 | 要素 |
|---|---|
| オンボーディング | 3枚: 価値説明 → 「使用中のみ」許可取得 → 常時許可への昇格説明(§7.1) |

### 7.1 権限取得フロー(重要)
1. 初回起動: 価値を説明した上で「使用中のみ」を要求(拒否率を下げる)
2. 初回記録成功後: 「アプリを閉じても記録を続けるには常時許可が必要」画面 → Always要求
3. Info.plist purpose string は具体的に書く: 「移動の記録を自動で続け、訪れた場所の霧を晴らすために位置情報を常に使用します。データは端末外に送信されません」

## 8. インポート / エクスポート

| 形式 | 方向 | 仕様 |
|---|---|---|
| Google タイムライン JSON | In | `latitudeE7/longitudeE7` および `"lat°, lng"` 文字列形式の両方に対応(プロトタイプのパーサを移植) |
| GPX | In / Out | trkpt/wpt/rtept 読取。エクスポートは全Pointをtrkとして出力 |
| CSV | In / Out | `timestamp,lat,lng,accuracy,source` |
| ネイティブバックアップ | Out | 全テーブルJSON(ファイルApp経由で保存) |

インポート時も §3.5 の統合記録パイプラインを通す(`policy = .historical` で鮮度フィルタのみ無効化し、重複排除・同一ID排除は適用する)。初期データとして並行稼働中のタイムラインを取り込み、記録の空白をなくす。

| バッテリー | L0〜L3 を全て有効にした常時記録で ≤1%/日、精密モード(L4)は ≤5%/時 |
| ストレージ | 5年運用で100MB未満(Point年5万件想定) |
| 描画 | 霧オーバーレイ含めマップ操作60fps、セル5万件で劣化なし |
| 起動 | バックグラウンド起動→記録完了まで3秒以内(§3.4) |
| プライバシー | 位置データの外部送信ゼロ。分析SDK不使用。App Privacy「データ収集なし」申告 |
| オフライン | 記録は完全オフライン動作。地図タイルのみ要ネットワーク(キャッシュはMapKit任せ) |

## 10. テスト設計

### 10.1 ユニットテスト
- GridEngine: 座標→cellKey変換(境界値: 0度またぎ、負値、粒度3種)
- 記録フィルタ: 精度棄却・重複排除の閾値境界
- Importer: タイムラインJSON 2形式 / GPX / CSV(壊れた行を含む)
- QuestEngine: 全踏破時・孤島状(飛び地)踏破時の探索終了、スコア順位

### 10.2 シミュレーションテスト(再現可能)
- Xcodeの位置シミュレーション用GPXを3本用意: ①久喜駅周辺散歩 ②電車移動(高速・低頻度) ③精度劣化を含む屋内
- GPXリプレイ→期待セル集合のスナップショットと突合(回帰テストとしてCIなしでも `⌘U` で再現)

### 10.3 フィールドテスト手順(7日間)
1. Day0: タイムラインJSONを初期投入、バッテリー記録開始(設定→バッテリーのスクショを毎晩)
2. Day1-7: 通常生活。手動操作禁止。毎晩「本日の新規Point数 / 新規セル数」に加え、**レイヤー(L0〜L3)別の採用件数と精度フィルタでの棄却件数**を統計画面で記録
3. 判定: 欠損日ゼロ・電池影響1%/日未満・L0〜L2由来Pointが合計1日20件以上あれば合格
4. L0 の棄却率を確認する。高すぎる場合の対処は §3.5 の方針(セル粒度の引き上げ)に従い、精度閾値は緩めない
5. L3 の実際の発火回数を記録する。1日1回未満が常態化する場合、L3 は保険として機能していないため §13 で扱いを再判断する
6. 週末にクエストを1回実行し、到達通知の発火を確認

### 10.4 電池・異常系
- 精密モード(L4)1時間連続でのバッテリー消費実測
- 権限格下げ→バナー表示、再許可→自動復帰
- 「正確な位置」OFF→専用バナー表示(§3.7)
- 強制終了後に L0/L2 で再起動して記録されること(実機のみ検証可)

## 12. リスク

| リスク | 影響 | 対策 |
|---|---|---|
| SLCの発火頻度が生活圏で低すぎる | セルが晴れない | L1(CLVisit)で滞在を拾い、L2(150m追尾ジオフェンス)でSLCの500m粒度の隙間を埋める。粒度1km表示で体感を補正 |
| BGAppRefreshが枯れてL3が発火しない | 滞在中の裏取りが欠ける | 記録の主軸はL0〜L2に置く設計(§3.3)。L3欠損は移動さえあれば実害なし。統計画面でレイヤー別の直近記録時刻を確認できるようにする |
| 常時許可の心理的ハードル | 記録開始できない | 段階的許可+送信ゼロの明示(§7.1) |
| iOSのバックグラウンド仕様変更 | 記録停止 | OSアップデート後にフィールドテスト§10.3を再実行する運用ルール |
| 霧描画のパフォーマンス | 操作感悪化 | タイル描画方式を採用済み。5万セル負荷試験をM2の完了条件に含める |
